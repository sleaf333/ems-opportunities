# Notes for Claude

Project owner is not a professional developer; explain changes in plain language and flag anything they must do by hand (Supabase dashboard, Cloudflare, SQL to run).

- Read PLAN.md for goals and the decisions log; update the log when a decision changes.
- Stack: Vite + React + TypeScript SPA on Cloudflare Pages; Supabase (Postgres, email OTP auth, RLS). Must stay on free tiers.
- All authorization lives in SQL (`supabase/migrations/`): RLS policies, column grants and SECURITY DEFINER functions (`set_my_signup`, `admin_set_member`). The UI only mirrors those rules for display; never rely on UI checks for security.
- Sign-ups: members write only through `set_my_signup`, which since 0012 allows just Interested and withdraw (eligibility by position, posting window and deadlines in America/Chicago). Joining is decided by the post's owners or admins: `owner_decide_signup(id, 'confirm' | 'not_selected' | 'undo' | 'remove')` and `owner_add_member(opp, email)`, both checking seats (`check_seat_available`). Status `committed` is shown as "Confirmed" and `not_selected` as "Reviewed by the lead" (never "rejected"); `waitlisted` is retired. UI: `LeadPeople` (src/components/LeadPeople.tsx) on My posts and the post page. Every change is logged to `signup_events` by trigger (changed_by = whoever decided). In a migration that adds an enum value, use it only inside plpgsql bodies: the Supabase SQL editor runs a file as one transaction.
- Labels: the database says partner / partnership_track; everything people see says Shareholder / Shareholder track / Shareholders only (labels in src/lib/format.ts; friendlyError rewrites DB messages). Never show "partner" wording.
- Partner (shown as Shareholder) is self-selected like any position (0003 removed the admin-only guard); admins can also set it via `admin_set_member`. Who can sign up is `opportunities.eligible_positions` (0004 replaced `audience`): everyone can view every post; only listed positions can mark Interested or Commit (enforced in `set_my_signup`). Presets live in `ELIGIBILITY_GROUPS` (src/lib/format.ts).
- Names on sign-ups: RLS lets members read only their own rows unless the post has `show_names`; admins and the post's owners see all. Counts for everyone come from `opportunity_counts()`.
- Owners (0005): `opportunity_owners` is the list of who can edit a post and see its names (check with `is_opp_owner(id)`); `created_by` is only who first posted it. The creator is added by trigger; owners and admins add via `add_opportunity_owner` (by email, must have signed in; promotes member to poster only when an admin adds), owners leave via `step_down_as_owner` (never the last owner), and only admins remove others (`admin_remove_opportunity_owner`). Since 0007 owners edit without the poster role; creating posts still needs poster. Ownership changes are logged to `owner_changes` by trigger (skips cascaded deletes). "My posts" is `/my-posts` (shown to posters, admins and anyone who owns a post).
- Owner presets (0013): `add_opportunity_owner` also accepts people who have not signed in (returns 'pending'); they wait in `owner_presets` (admins and the post's owners can read; `remove_owner_preset` cancels) and `handle_new_user` makes them owners at first sign-in. Committee leads were set in bulk with `supabase/scripts/set_committee_leads.sql` (preview first, then `v_apply := true`; all-or-nothing when a name is unmatched or ambiguous).
- Member lists (0014): confirmed sign-ups are each committee's member list (the record of who serves where; a future data source for shareholder involvement). Leads find people with `find_people(query)` (owners of any post and admins only; profiles by name or email plus `member_presets` emails; max 8) through `PersonPicker` (src/components/PersonPicker.tsx), used in LeadPeople and the Owners box. `owner_add_member` puts people who have not signed in into `pending_members` (returns 'pending'; counts toward seats; `remove_pending_member` cancels); `handle_new_user` turns them into confirmed sign-ups at first sign-in, with the event credited to the lead and dated when they were added. `'remove'` takes a confirmed member off the list (status withdrawn, logged; replaces Undo on confirmed rows). `confirm_roster(opp)` records "List is up to date" in `roster_checks`; the UI asks again after 335 days, and `run_daily_notifications` emails owners in November (on their digest day) about lists not confirmed in 330 days (log kind `roster_check`, at most one per 300 days). Admin "Export member lists" is the CSV. Backup `schema_version` 14, 20 tables. The What we track page does not mention member lists yet (owner's choice).
- Suggestions (0015): any signed-in member calls `suggest_person(opp, email, note)` (SuggestPerson on the post page) and the colleague gets one email at once (also people who never signed in; kind 'suggestion' in `notification_log`, counts toward the daily cap). Returns 'sent', 'already_in' (interested, confirmed, attended or waiting to sign in) or 'already_suggested' (anyone, same post, 365 days); refuses closed or expired posts, own email, other domains, positions not eligible (profile or preset), people with `email_opt_in = false`, more than 10 a day per sender and 3 in 30 days per person. Own admin switch `notification_settings.suggestions_enabled` (`admin_set_suggestions`; not tied to the reminder switch); `suggestions_available()` decides whether the box shows. `suggestions` is readable by the suggester, the post's owners (LeadPeople "Suggested by members") and admins. `find_people` is open to every signed-in member since 0015. `erase_member_permanently` also clears suggestions, pending_members and owner_presets by email. Backup `schema_version` 15, 21 tables.
- Service record (My sign-ups): built in the browser by `buildServiceRecord` (src/lib/serviceRecord.ts) from the member's own `signup_events` and `opportunity_owners`; no table of its own. A stint starts at a change to committed and ends at any later change away from it; attended (completed) is "Took part"; owning a post is "Lead". Print uses `window.print()` with print CSS (not a blocked pop-up).
- Nothing is deleted: no DELETE on opportunities or interest_categories; expiry is `visible_until` (null = indefinitely), close/archive via status.
- Safety net (0006): FKs from signups, signup_events and member_interest_categories are `on delete restrict`, so Supabase "Delete user" (or deleting a post) with any activity fails. Real deletions only via `erase_member_permanently` / `erase_opportunity_permanently` (SQL editor only; execute revoked). Triggers log post edits to `opportunity_history` and role changes to `role_changes` (admin-only SELECT). `admin_export_all()` is the full backup (logs to `backup_log`); when adding a table, add it there too and bump `schema_version` (a DB test counts tables).
- Supabase returns at most 1,000 rows per request: load growing tables with `pageThrough` (src/lib/data.ts) and a stable order ending in a unique column.
- Contacts (0008): `opportunities.contacts` is a jsonb list of `{name, email}` (max 10, check constraint; anyone, not only site users; separate from owners). The form mirrors the first contact into the old `contact_name` / `contact_email`; read contacts with `contactsOf()` and validate with `cleanContacts()` (src/lib/format.ts).
- Advance settings (0009): `member_presets.position` holds any position, applied by `handle_new_user` at first sign-in (`is_partner` is kept in step for the Admin checkbox). Bulk lists use `supabase/scripts/set_*.sql` (rank: Shareholder > Shareholder track > Employed physician; never downgrade, never change roles).
- Posting requests (0010): members call `request_posting(note)` (one pending per person); admins use `admin_decide_post_requests(ids, approve)` (approve promotes member to poster, never touches admins; logged in role_changes). `post_requests` keeps every request; members read their own, admins all. Layout shows admins the pending count next to Admin (links to `/admin#requests`).
- Reminder emails (0011): owners tick Contacted on My posts (`set_contacted`, columns `signups.contacted_at/contacted_by`; not a status change, so no signup_events). `run_daily_notifications(p_now)` (pg_cron 13:00 UTC) sends owner digests on each owner's day of a 14-day cycle (md5 of their id) and one member follow-up (`nudged_at`) 21 to 42 days after signing up; both skip `profiles.email_opt_in = false`, closed or expired posts, and owners' own sign-ups; capped by `notification_settings.daily_cap`. `send_email` posts to Brevo via pg_net with the key from Vault secret `brevo_api_key` (never in the repo); `record_notification_results` copies answers from `net._http_response` into `notification_log`. Admins use `admin_notification_status` / `admin_set_notifications` / `admin_send_test_email` (Admin card `EmailReminders`). Supabase rejects UPDATE/DELETE without WHERE from API calls (pg_safeupdate): always add one, even on single-row tables. Emails are plain inline-styled HTML, no em dashes. The DB tests stub net/vault/cron in `supabase_stub.sql`.
- Wording: "role" (member / poster / admin) is what someone can do on the site and is shown as "site role", with admin labelled "Site admin" so it is never confused with the Administrative staff position. "Position" is someone's job (physician, APC, Administrative staff). Granting Site admin asks for confirmation; keep it to a few people.
- Never use browser pop-ups (`window.confirm` / `prompt` / `alert`): in-app browsers (Outlook on iPhone) silently block them, which once made "Withdraw" do nothing. Ask on the page with `ConfirmAction` (src/components/ConfirmAction.tsx); a unit test scans src/ for pop-ups.
- Loading: `useLoader` wraps loaders in `withRetry` (src/lib/data.ts: 2 retries, refreshing the sign-in between tries) and pages show `LoadError` with Try again. The Supabase client's own retries are off (`db: { retry: false }`) so the two don't stack.
- Topics and member interests use `interest_categories` (+ join tables), written via `set_opportunity_categories` / `set_my_interests`.
- In SQL, compare possibly-null owners with `coalesce(x = auth.uid(), false)`; a bare `=` inside `not (...)` let a poster edit seeded (ownerless) posts once.
- Sign-in is a 6-digit email code (verifyOtp type 'email'), limited to @ems-wi.com by a trigger on auth.users.
- After launch, schema changes go in a new numbered migration; never edit an applied one.
- Checks before pushing: `npm run build`, `npm run test:unit` (Vitest, pure logic such as `src/lib/insights.test.ts`) and `npm run test:db` (add tests to `supabase/tests/permissions_test.sql` for new rules).
- Admin Insights (`/admin/insights`): all math lives in `src/lib/insights.ts` (tuning constants at the top); charts are hand-made SVG in `src/components/insights/`. Chart colors `--series-interest` / `--series-commit` passed the dataviz palette validator for light and dark surfaces; re-run it if they change. Funnel and heatmap use one hue (brand) in steps. "Committees at a glance" (`committeeHealth`, `CommitteeHealth.tsx`) lists committee and leadership posts (open or closed) with leads (`AdminData.owners`), members (position filter applies), seats, waiting, suggestions in 90 days and the last list check; flags no lead, no members, waiting over 14 days, list check due (a year after the last check, or after the first current lead was added) and full. No emails, no SQL.
- Site help contact (Sam Leaf, samuel.leaf@ems-wi.com) is `HELP_CONTACT` in src/lib/format.ts, shown by `HelpContact` in the footer, sign-in page, LoadError and the What we track page; change it there only.
- Writing for the owner or the group: no em dashes.
- Supabase grants anon/authenticated EXECUTE on new public functions by default: in each new migration, revoke from public/anon/authenticated and grant back only what the site calls.
- Motion: JS effects (`Celebrate`, `CountUp`, `src/lib/motion.ts`) must check `prefersReducedMotion()`; the CSS reduce-motion rule only stops CSS animations. The burst draws in a fixed, overflow-hidden, pointer-events-none layer so it never scrolls the page or blocks clicks.

Fonts are free lookalikes: Syncopate (wide caps headings), Cormorant Garamond italic (taglines), Figtree (body).
